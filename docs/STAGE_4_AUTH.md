# 4/10단계 — 회원가입 / 로그인

## 구현 범위

- `/account`: 이메일/비밀번호 로그인과 계정 화면.
- `/account?mode=signup`: 가입, 비밀번호 확인, 개인정보 안내 확인, 선호 언어 / 학생 유형 / 관심 국가 커뮤니티 선택.
- `/account?mode=reset`: 이메일로 비밀번호 재설정.
- `/privacy`: 네 언어의 데이터 처리 / 탈퇴 / 브라우저 저장 안내.
- 이메일 인증 메일 발송 / 재전송과 상태 갱신, 로그아웃, Firebase의 브라우저 로컬 인증 유지.
- 설정 조회 실패 시 덮어쓰기 방지, 가입 성공 뒤 설정 / 메일만 실패했을 때 복구, 초기 연결 실패 재시도.
- 최근 비밀번호 재인증을 거친 탈퇴, 서버 개인 기록 정리, Auth 계정 삭제, 중간 실패 후 재시도.

이메일 인증은 재학 인증이 아닙니다. 학교 이메일 / 실명 / 학번 / 서류를 요구하지 않습니다. 커뮤니티는 아직 열지 않았고 인증된 계정도 글 / 채팅을 쓸 수 없습니다. 북마크 / 체크리스트는 기존 브라우저 저장을 유지하며 계정 동기화는 5단계 작업입니다.

## 자동 검증

```powershell
npm test
npm run test:rules
npm run test:auth
npm run build
```

`test:auth`는 Auth와 Firestore Emulator를 함께 실행합니다. 테스트 데이터는 고정된 `demo-ku-bridge`와 루프백 포트에서만 만듭니다. 실제 프로젝트 계정 / 문서는 테스트용으로 생성하지 않습니다. Windows Java의 IPv6 소켓 오류를 피하기 위해 실행 스크립트에서 해당 프로세스에만 `-Djava.net.preferIPv4Stack=true`를 적용합니다.

Emulator는 실제 받은편지함으로 메일을 보내지 않습니다. 검증 / 재설정 코드를 가져와 실제 Firebase SDK로 적용하고 상태와 비밀번호 변경을 검사합니다. SDK 세션을 재사용한 서비스 재마운트는 검사하지만 브라우저 재시작 후 저장소 복구는 아래 공개 환경에서 별도로 확인합니다.

## 사용자가 진행할 순서

### 1. 코드 반영과 공개 배포

이번 변경사항을 기존 방식으로 커밋하고 `main`에 푸시합니다. `.env.local`은 제외 상태를 유지합니다. Cloudflare Pages가 새 커밋을 빌드 / 배포해 성공했는지 확인합니다. 추가 환경변수나 별도 서버 생성은 필요하지 않습니다. Firebase 규칙 배포 상태는 `VALIDATION.md`에 기록합니다.

### 2. 본인 이메일로 가입

1. `https://ku-bridge.pages.dev/account?mode=signup`을 엽니다.
2. 메일을 받을 수 있는 본인 주소와 8자 이상 비밀번호를 입력합니다. 비밀번호는 대화에 보내지 않습니다.
3. 비밀번호 확인, 언어 / 학생 유형 / 관심 국가 선택을 입력합니다.
4. 개인정보 안내를 확인한 뒤 확인란을 체크하고 가입합니다.
5. 계정 화면에 이메일과 `이메일 인증 필요`가 표시되는지 확인합니다.

가입 직후 설정 저장이나 메일 발송만 실패했다면 계정이 이미 만들어졌을 수 있습니다. 반복 가입하지 말고 계정 화면의 설정 저장 / 인증 메일 재전송 또는 로그인 / 비밀번호 재설정을 사용합니다.

### 3. 실제 인증 메일 확인

1. 받은편지함과 스팸함에서 Firebase 인증 메일을 찾습니다.
2. 메일의 링크를 열어 인증을 완료합니다. 기본 Firebase 처리 페이지가 열리는 것은 정상입니다.
3. KU Bridge의 계정 화면으로 돌아와 `인증 상태 확인`을 누릅니다.
4. `이메일 인증 완료`로 바뀌는지 확인합니다. 재전송 뒤에는 같은 화면에서 60초간 재전송 버튼이 잠깁니다.

### 4. 로그인 유지 / 설정 / 로그아웃

1. 계정 설정을 변경하고 저장합니다.
2. 페이지를 새로고침하고 로그인 상태와 설정이 유지되는지 확인합니다.
3. 브라우저 탭을 닫았다가 다시 열고 확인합니다. 시크릿 모드나 사이트 데이터 자동 삭제 설정은 저장 유지에 영향을 줄 수 있습니다.
4. 로그아웃 후 다시 로그인합니다. 이메일과 인증 상태 / 계정 설정이 복구되는지 확인합니다.
5. 비회원 북마크와 체크리스트는 그대로 이 브라우저에 있으며, 계정 기록으로 자동 이전됐다고 표시하지 않는지 확인합니다.

### 5. 실제 비밀번호 재설정

1. 로그아웃하고 로그인 화면의 `비밀번호 재설정`을 누릅니다.
2. 가입한 이메일을 입력하고 메일을 보냅니다.
3. 실제 메일 링크에서 새 비밀번호를 설정합니다.
4. 새 비밀번호로 로그인되는지 확인합니다. 화면의 발송 안내는 이메일 가입 여부를 공개하지 않는 공통 문구입니다.

### 6. 탈퇴 확인

탈퇴 시험은 삭제해도 되는 본인 테스트 계정으로 진행합니다.

1. 내 계정 → `회원 탈퇴`를 누릅니다.
2. 삭제 안내를 확인하고 현재 비밀번호와 확인란을 입력합니다.
3. `개인 데이터와 계정 삭제`를 누릅니다.
4. 완료 안내와 로그아웃 상태를 확인합니다.
5. 삭제한 계정의 이전 비밀번호로 로그인할 수 없는지 확인합니다.

서버 정리 중 실패하면 일부 데이터가 이미 지워졌을 수 있습니다. 탈퇴 진행 중 안내가 남아 있는 계정으로 다시 로그인하고 비밀번호를 입력해 재시도합니다. 성공 안내가 나오기 전에는 탈퇴 완료로 간주하지 않습니다.

### 7. 결과 전달

배포된 커밋과 함께 `가입 / 인증 메일 / 새로고침 유지 / 로그아웃 / 재설정 / 탈퇴 확인 완료` 여부를 알려 주면 4단계 외부 검증을 닫고 5단계 동기화로 진행합니다. 실패했다면 어느 동작에서 나온 오류인지와 화면 문구를 보내 주세요. 비밀번호 / 메일 인증 링크 / 재설정 코드는 보내지 않습니다.

## 탈퇴 처리와 후속 단계 계약

탈퇴 전 비밀번호를 다시 확인하고 토큰을 갱신합니다. 본인 UID의 `accountDeletions/{uid}`에 서버 시각을 기록해 다른 탭 / 이전 토큰의 프로필과 개인 기록 생성 / 수정을 막습니다. 이후 `saved` / `checklists` 하위 문서, 프로필, Auth 계정 순서로 정리합니다. 마지막 Auth 삭제가 실패하면 삭제 표식을 유지해 다음 로그인에서 재시도할 수 있습니다.

삭제 기록은 내부 UID와 요청 시각만 담고 이메일 / 글 / 개인 설정은 담지 않습니다. 이전 세션의 재기록 방지용 비공개 처리 기록이며 일반 클라이언트는 이를 삭제 / 수정할 수 없습니다. 이 기록의 별도 보관 사실을 개인정보 안내에 표시합니다. 관리자 / 이용 제한 기록이 있는 계정은 이 일반 탈퇴 경로에서 지우지 않습니다.

현재 공개 게시글 / 채팅 데이터는 없습니다. **새 개인 컬렉션이나 공개 커뮤니티 쓰기를 열기 전에**, 해당 데이터의 `accountDeletions` 쓰기 차단과 작성자 연결 / 보관 / 삭제 정책 및 정리 경로를 반드시 확장해야 합니다. 클라이언트 탈퇴 처리는 여러 서비스에 걸친 원자적 작업이나 서버의 예약 정리를 제공하지 않습니다. TTL / Functions / 결제 계정은 추가하지 않았습니다.
